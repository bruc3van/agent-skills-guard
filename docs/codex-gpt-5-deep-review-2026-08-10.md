## Findings

### R1 — P1：仓库自动更新可能继续扫描旧 commit

证据位置：

- `src-tauri/src/services/github.rs:590-609`
- `src-tauri/src/services/github.rs:829-870`
- `src-tauri/src/commands/mod.rs:261-320`

`download_repository_archive()` 会将新 zipball 直接解压到既有的 `extracted/`，没有先清理旧目录，也没有通过临时目录进行原子替换。远端 SHA 变化触发普通自动刷新时，会产生以下状态：

1. 新旧 commit 根目录同时存在于 `extracted/`。
2. 旧 `.commit_sha` 仍然存在，`extract_commit_sha_from_cache()` 会优先返回旧 SHA。
3. `find_repo_root()` 返回 `read_dir()` 枚举到的第一个目录，无法保证选择新 commit。
4. 数据库可能继续保存旧 SHA，后续扫描再次判断远端有更新并重复下载。

因此，用户可能在上游已经更新后仍看到旧 Skills，或者进入持续重复下载但缓存基线不前进的状态。显式执行“清除缓存后刷新”会绕过该问题，但普通自动更新路径不会。

建议修复：

- 将归档解压到同一文件系统中的唯一临时目录。
- 只从本次下载产生的根目录推导 commit SHA，不读取旧 `.commit_sha`。
- 完整解压并校验成功后，原子替换既有 `extracted/`。
- 为“旧 SHA → 新 SHA”连续两次下载增加回归测试，断言只剩一个根目录、返回新 SHA 且扫描结果来自新目录。

### R2 — P1：更新覆盖失败时可能保留未扫描的旧文件

证据位置：`src-tauri/src/services/skill_manager.rs:2773-2808`。

更新确认阶段先扫描 staging 目录并生成 `scan_report`。当目标目录需要清空而 `remove_dir_all()` 失败时，当前实现只记录 warning，随后继续调用 `copy_dir_recursive()` 覆盖写入，并将更新标记为成功。

这会使 staging 中已经删除、因而未进入本次安全扫描的旧文件继续残留在实际安装目录。最终数据库保存的是 staging 的安全报告，但真实可执行目录是“新文件 + 残留旧文件”的合并结果。

建议修复：

- 目标目录清理失败时立即终止更新，并恢复已创建的备份。
- 不允许将目录合并写入作为更新降级路径。
- 更稳妥的实现是准备完整新目录后，通过 rename 原子替换。
- 增加回归测试：旧版本包含危险脚本，新版本删除该脚本，模拟目标目录清理失败，断言更新失败、旧安装完整恢复且数据库安全报告不变。

### R3 — P1：单路径卸载可删除未登记的任意路径

证据位置：

- `src-tauri/src/commands/mod.rs:719-727`
- `src-tauri/src/services/skill_manager.rs:1609-1636`

`uninstall_skill_path` Tauri command 接受 renderer 提供的 `skill_id` 和 `path`。后端取得 skill 后，直接对输入路径调用 `remove_dir_all()`、`remove_file()` 或链接删除逻辑，没有先证明该路径属于对应 skill 的 `local_paths` 或 `local_path`。

这意味着只要有一个有效 `skill_id`，IPC 调用者就能要求后端递归删除任意可写目录。正常 UI 当前传入的是记录中的路径，但文件删除权限边界不能依赖前端始终正确，也不能依赖 renderer 永远不被注入或误调用。

建议修复：

- 在执行任何文件系统操作之前，规范化请求路径和数据库记录路径。
- 要求请求路径与该 skill 的一个已登记路径完全匹配；不能只使用字符串前缀判断。
- 对链接使用 `symlink_metadata`，避免规范化过程意外把删除目标切换到链接源。
- 拒绝空路径、根目录、用户主目录以及无法归属到该 skill 的路径。
- 增加任意临时目录、父目录、相似前缀目录和合法已登记路径的测试矩阵。

### R4 — P2：单路径卸载失败仍删除追踪元数据

证据位置：`src-tauri/src/services/skill_manager.rs:1638-1680`。

文件删除错误会先写入 `errors`，但实现随后仍从 `local_paths` 删除该路径并保存 skill，最后才检查 `errors` 并返回 `UNINSTALL_PATH_PARTIAL_FAILURE`。

因此，文件系统删除失败后，残留目录仍在磁盘上，但数据库已经丢失该路径。用户再次操作时无法通过应用重试卸载。这与完整卸载 `uninstall_skill()` 已经采用的“所有删除成功后才清空元数据”原则不一致。

建议修复：

- 删除失败时原样保留 skill 元数据并立即返回 partial-failure。
- 只有确认路径删除成功后，才更新 `local_paths`、`local_path` 和 `installed`。
- 增加与 `uninstall_failure_preserves_installed_skill_metadata` 对称的单路径卸载回归测试。

### R5 — P1：ZIP 解压没有解压后资源预算

证据位置：`src-tauri/src/services/github.rs:558-650`。

下载阶段将压缩包大小限制为 100 MiB，但解压阶段没有限制：

- ZIP 条目数量；
- 单个条目的声明或实际解压大小；
- 所有条目的累计解压大小。

每个文件通过无上限的 `std::io::copy()` 写入磁盘。高度压缩的恶意仓库可以在安全扫描开始前耗尽磁盘空间。路径遍历检查只能阻止写出目标目录，不能防止资源耗尽。

建议修复：

- 设置最大条目数、单条目解压上限和累计解压上限。
- 同时检查 ZIP metadata 声明大小与实际写入字节数，不能只信任声明值。
- 解压到临时目录；任何超限或写入失败都清理临时目录，不污染现有缓存。
- 增加高压缩比、超多空文件、伪造 size metadata 和累计超限测试。

## 建议修复顺序

1. R2：先封住“安全报告与实际安装内容不一致”的更新路径。
2. R3：收紧递归删除的 IPC 权限边界。
3. R1：将仓库缓存刷新改为临时目录加原子替换。
4. R5：复用 R1 的临时解压流程，同时加入资源预算。
5. R4：统一完整卸载与单路径卸载的 partial-failure 持久化语义。

R1 与 R5 都位于归档下载/解压链路，适合在同一实现中修复；R3 与 R4 位于同一卸载函数，也适合共享一组路径验证和失败恢复测试。
